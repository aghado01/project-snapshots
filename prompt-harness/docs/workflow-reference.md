# Prompt Harness Workflow Reference

This project assumes the portable PowerShell bootstrap is the authoritative local environment. Local scripts do not rely on VS Code Python discovery or on bare `python` resolving correctly from `PATH`.

## Python Resolution

Use `scripts/python.ps1` for project Python calls. Local development uses one canonical `.venv`; dependency tiers are not part of the normal workflow.

Resolution order:

1. `.venv\Scripts\python.exe` or `.venv/bin/python`
2. `PROMPT_HARNESS_PYTHON`
3. `PYENV_ROOT\versions\PYENV_VERSION\python.exe`
4. `PORTABLE_ROOT\PyenvPython\pyenv-win-PYTHON_VERSION\versions\PYTHON_VERSION\python.exe`
5. First non-WindowsApps `python.exe`, `python`, or `python3` on `PATH`

Current expected local interpreter:

```powershell
C:\Users\azrie\PDenv\PyenvPython\pyenv-win-3.12.6\versions\3.12.6\python.exe
```

Useful commands:

```powershell
pwsh scripts/resolve_python.ps1
pwsh scripts/ensure_venv.ps1
pwsh scripts/ensure_venv.ps1 -CheckOnly
pwsh scripts/python.ps1 --version
pwsh scripts/run_tests.ps1
```

The wrapper sets `PYTHONNOUSERSITE=1` and `PIP_USER=0` if they are not already set, matching the portable bootstrap assumptions.

`scripts/ensure_venv.ps1` is the source of truth for creating and updating the local environment. It uses the portable resolver as the bootstrap interpreter, installs `requirements-dev.txt`, and writes `.venv/.prompt-harness-env.json` with requirement fingerprints so `-CheckOnly` can fail clearly when the environment is stale.

## Default Local Run Mode

Local automation should usually launch in the background and write artifacts instead of holding a console open. Use `scripts/start_background_run.ps1` for tests, probe generation, inventory refreshes, local model runs, and other commands that may produce noisy output or wait on an endpoint.

```powershell
pwsh scripts/start_background_run.ps1 -Name tests -ScriptPath scripts/run_tests.ps1
pwsh scripts/get_background_run.ps1
```

Run artifacts are written under:

```text
reports/runs/<run-id>/metadata.json
reports/runs/<run-id>/status.json
reports/runs/<run-id>/stdout.log
reports/runs/<run-id>/stderr.log
```

Arguments after the launcher parameters are passed through to the target script:

```powershell
pwsh scripts/start_background_run.ps1 -Name rubric-tests -ScriptPath scripts/run_tests.ps1 tests/unit/test_rubric_engine.py -q
pwsh scripts/start_background_run.ps1 -Name instruction-failure -ScriptPath scripts/python.ps1 -m src.runners.batch --prompts data/prompts/instruction_failure --out reports/instruction-failure-smoke --config configs/providers.yaml
```

Foreground scripts are still valid for CI and for short manual checks where an immediate exit code is the desired artifact.

## Local Eval Commands

```powershell
pwsh scripts/start_background_run.ps1 -Name baseline -ScriptPath scripts/run_baseline.ps1
pwsh scripts/start_background_run.ps1 -Name gates -ScriptPath scripts/compare_gates.ps1 -Candidate reports/candidate-test
pwsh scripts/start_background_run.ps1 -Name local-smoke -ScriptPath scripts/python.ps1 -m src.runners.batch --provider llama_cpp --model local-model --out reports/local-smoke --prompts data/prompts
pwsh scripts/get_background_run.ps1
```

The default provider remains `echo` for deterministic CI. Local model runs should use `--provider llama_cpp` after the corresponding server is running.

## Context Probe Generation

Context-window/tokenizer probes are generated by Python modules under `src/probes`. The PowerShell entrypoint is:

```powershell
pwsh scripts/start_background_run.ps1 -Name probe-generation -ScriptPath scripts/generate_probe_payloads.ps1 -EnsureVenv
```

Outputs:

```text
data/probe_payloads/          raw probe payload artifacts
data/prompts/context_probes/  harness-readable JSONL prompt fixtures
```

Line-indexed payload suites default to template rendering, not `json.dumps`, because malformed JSON strings and unescaped boundary cases are valid probe surfaces. Use `-RenderMode structured` only when valid JSON serialization is the experiment you want.


Relevant environment variables:

```powershell
LLAMA_CPP_BIN=D:\ or portable llama.cpp bin path set by ps.core.bootstrap

```

The GGUF inventory root is expected to be:

```powershell
D:\models\gguf
```

The current local GGUF set is tracked in `data/model_inventory.json`; prefer that file over hardcoded model lists in docs.

## Model Inventory

The tracked local model registry is:

```text
data/model_inventory.json
```

Refresh it locally:

```powershell
pwsh scripts/start_background_run.ps1 -Name model-inventory -ScriptPath scripts/refresh_model_inventory.ps1
```

Optional SHA256 hashing is available but can be slow for large GGUF files:

```powershell
pwsh scripts/start_background_run.ps1 -Name model-inventory-sha256 -ScriptPath scripts/refresh_model_inventory.ps1 -IncludeSha256
```

The GitHub Actions workflow `.github/workflows/model-inventory.yml` is designed for a self-hosted Windows runner that can see `D:\models\gguf`. GitHub-hosted runners cannot see local disk inventory, so the job intentionally uses `runs-on: [self-hosted, Windows]`.

## VS Code Status

VS Code Python discovery is currently not treated as authoritative for this project. The durable path is the explicit PowerShell wrapper. VS Code settings can later be pointed at the resolved interpreter, but the project scripts should keep working without that.
