# Prompt Harness Orientation

This file is the fast orientation guide for contributors and coding assistants working in this repo.

## Operating assumptions

- Treat the portable PowerShell environment as authoritative.
- Do not rely on VS Code Python interpreter discovery being correct.
- Do not rely on bare `python` from `PATH`.
- Prefer repo-local scripts over ad hoc commands so runs stay reproducible.
- For local automation, prefer launching background runs that write status and logs under `reports/runs/` instead of awaiting noisy terminal output.

## Python workflow

- Use `scripts/python.ps1` for any Python invocation.
- Use `scripts/run_tests.ps1` for tests.
- Use `scripts/ensure_venv.ps1` to create or update the single local development `.venv`.
- `scripts/install_deps.ps1` is only a compatibility wrapper around `ensure_venv.ps1`.

Examples:

```powershell
pwsh scripts/python.ps1 --version
pwsh scripts/ensure_venv.ps1
pwsh scripts/run_tests.ps1
pwsh scripts/python.ps1 -m src.runners.batch --config configs/providers.yaml --prompts data/prompts --out reports/test-run
```

Preferred local run mode for tests, probes, inventory refreshes, and model experiments:

```powershell
pwsh scripts/start_background_run.ps1 -Name tests -ScriptPath scripts/run_tests.ps1
pwsh scripts/get_background_run.ps1
```

Each background run writes `metadata.json`, `status.json`, `stdout.log`, and `stderr.log` under `reports/runs/<run-id>/`. CI may still call foreground scripts directly because CI needs process exit codes.

Interpreter resolution is intentionally explicit and derived from environment variables such as:

- `PROMPT_HARNESS_PYTHON`
- `PYENV_ROOT` + `PYENV_VERSION`
- `PORTABLE_ROOT` + `PYTHON_VERSION`

## VS Code integration

- VS Code Python integration is not the source of truth for this project.
- The durable path is the explicit PowerShell wrapper.
- If editor state disagrees with the wrapper, trust the wrapper and fix editor wiring later.

## Evaluation workflow

- The deterministic default provider for CI and local smoke runs is `echo`.
- Local model experimentation should be explicit, usually via the `llama_cpp` provider entry in `configs/providers.yaml`.
- Typical local regression flow:

```powershell
pwsh scripts/run_baseline.ps1
pwsh scripts/python.ps1 -m src.runners.batch --out reports/candidate-test --prompts data/prompts --config configs/providers.yaml
pwsh scripts/compare_gates.ps1 -Candidate reports/candidate-test
```

## Context probe workflow

- Context probes are generated by `src/probes` and orchestrated with `scripts/generate_probe_payloads.ps1`.
- Raw payloads go under `data/probe_payloads/`; harness JSONL prompt fixtures go under `data/prompts/context_probes/`.
- Template-rendered payload mode is intentional for line-indexed probes because malformed JSON and raw escaping boundaries can be the test surface.

```powershell
pwsh scripts/generate_probe_payloads.ps1 -EnsureVenv
```

## Instruction failure workflow

- Mercury-inspired instruction-failure fixtures live under `data/prompts/instruction_failure/`.
- They use `turns[]` plus `system_prompt`; the runner renders a transcript for echo and passes structured chat messages to OpenAI-compatible providers.
- Keep safety-robustness fixtures tagged with `model_applicability.exclude_tags: [abliterated]` only for model variants whose refusal behavior has actually been removed; do not assume that from the family name alone.

```powershell
pwsh scripts/python.ps1 -m src.runners.batch --prompts data/prompts/instruction_failure --out reports/instruction-failure-smoke --config configs/providers.yaml
```

## llama.cpp usage

- The sibling workspace folder `llama.cpp-build` contains local launcher and benchmark scripts.
- Local GGUF discovery expects `$env:LLAMA_CPP_MODELS\gguf`, falling back to `D:\models\gguf`.
- The checked-in local model registry is `data/model_inventory.json`.
- Refresh it with:

```powershell
pwsh scripts/refresh_model_inventory.ps1
```

## CI expectations

- Main CI uses the same explicit wrapper approach instead of bare `python`.
- Local GGUF inventory cannot be refreshed on GitHub-hosted runners.
- Model inventory refresh is handled by a separate self-hosted Windows workflow.

## When changing automation

- Preserve explicit Python invocation.
- Preserve the ability to run locally without depending on editor state.
- Preserve the background-run/status-file pattern for local automation defaults.
- Preserve the distinction between deterministic CI behavior and local-model-first experimentation.
- Preserve template rendering for probe payload families that intentionally need invalid JSON or raw string boundary cases.
- Preserve the distinction between instruction-following failures and factual hallucinations in Mercury-style fixtures.
